# Study Hall 개발 의도와 변경 계약

최종 대조: 2026-09-25. Claude·Codex 공통 기준. 이 문서는 **유지해야 할 의도와 연결 관계**이며, 모든 기능의 무결함·운영 검증 완료를 선언하지 않는다. 현재 코드·DB·테스트 상태는 [CURRENT_STATE.md](CURRENT_STATE.md), 학원 설정 원칙은 [ACADEMY_TEMPLATES.md](ACADEMY_TEMPLATES.md)를 함께 읽는다.

## 1. 개발 목적과 의사결정 순서

학원이 납품받은 뒤 시간표·출결·휴대폰·상벌점·휴무·좌석·수납·시험을 자체 설정으로 운영하는 범용 제품이다. 경찰은 먼저 적용한 학원이지 공통 코드의 기본 규정이 아니다.

1. 사용자의 최신 명시적 요구를 우선한다. 이전 채팅의 반대 요구는 최신 결정으로 대체한다.
2. 학원별 독립 설정·기존 원장 보호·권한 분리 계약을 확인한다.
3. 현재 라우트부터 실제 서비스·저장소·재계산·조회 경로를 추적한다.
4. 문서와 코드가 다르면 차이를 기록하고, 문서에 맞추려고 기존 정상 동작을 임의로 바꾸지 않는다.
5. 미확인 운영 상태를 추정해 마이그레이션·초기화·일괄 재계산하지 않는다.

기본은 **단일 담당자가 구현부터 검증까지** 수행한다. 광범위 리팩터링보다 재현된 문제의 최소 수정을 우선한다. 개선 제안 자체는 구현·배포 승인이 아니다.

## 2. 설정과 운영 데이터의 경계

- 기존 설정 허브와 편집 화면을 재사용한다. 템플릿 기능 때문에 같은 값을 편집하는 별도 설정 체계를 만들지 않는다.
- 템플릿은 설정 사본이다. 적용 후 원본 템플릿·타 학원 변경을 자동 전파하지 않는다.
- 설정에는 사용 여부·요일·교시·점수·적용일·자동/관리자 확정 방식이 포함된다. 규칙 ID도 해당 학원 소유인지 검사한다.
- 학생 개인정보, 출결·성적·수납·좌석 배정 원장은 템플릿 복제 대상이 아니다.
- 변경 전후 미리보기, 적용일, revision 충돌 검사, 이력을 유지한다. 과거 적용일과 적용일 정정도 지원한다.
- 설정 저장과 과거 운영 원장 재계산은 별개다. 과거 재계산은 승인된 범위와 날짜를 기록하고 같은 계산 서비스를 사용한다.
- 현재 설정만 읽어 과거 기록을 판정하지 않는다. 날짜별 이력과 당시 교시·규칙·점수, KST 날짜 경계를 함께 사용한다.

주요 경로: `lib/services/academy-template.service.ts`, `academy-configuration-history.service.ts`, `management-policy.service.ts`, `settings.service.ts`, `components/settings/ConfigurationReview.tsx`.

## 3. 사용자별 접근 계약

| 사용자 | 업무 범위 | 반드시 유지할 제한 |
|---|---|---|
| 최고 관리자 | 허용된 학원 운영 관리 | 매 요청의 대상 학원 확인 |
| 관리자 | 소속 학원 설정·운영·정정 | 타 학원 학생·규칙·기록 ID 참조 거부 |
| 조교 | 소속 학원 현장 출석·휴대폰 등 허용 업무 | 관리자 설정 권한으로 확대하지 않음. 과거 수정 허용 범위는 설정 유지 |
| 학생 | 본인 출결·등원·상벌점·성적·학습 기록 | 요청 studentId를 믿지 않고 세션 본인과 대조. 다른 학생 비교 정보는 익명화 |
| 공용 등원 기기 | 승인된 기기에서 수험번호 등원 입력 | 관리자 로그인과 별개. 승인·만료·해제 검사 유지 |

API 인증과 서버 소유권 검사를 생략하고 UI에서만 숨기는 수정은 허용하지 않는다. 학생에게 반 전체 원자료를 보내고 브라우저에서 필터링하지 않는다.

## 4. 출석·수업·시험·상벌점 연결

### 원본과 파생 기록

출결 저장 → 해당 날짜 설정 조회 → 출결 벌점·개근·시험 연동의 해당 경로 재계산 → 상벌점 원장 → 관리자 부여 내역·학생별 순위·개인 내역·경고 계산.

- `attendance.service.ts`가 출결 저장 및 파생 계산의 연결점이다. 파생 계산 실패 시 출결이 저장됐는지와 계산이 실패했는지를 구분해 알린다. 실패를 숨기거나 UI에서 임의로 점수만 보정하지 않는다.
- 일반 출결 벌점: `policy-attendance.service.ts`의 `applyPolicyAttendancePoints` / `confirmPolicyAttendance`. 자동 모드는 저장·마감 시 계산한다. 관리자 확인 모드는 후보와 확정을 분리한다.
- 같은 저장 재시도는 중복 점수를 만들면 안 된다. 동일 자동 기록은 가능한 한 ID·생성 시각을 유지한다. 정정 후 근거가 사라진 **해당 자동 벌점만** 회수한다.
- 수동 부여 점수, 다른 자동화의 점수, 다른 학원 기록을 함께 삭제하지 않는다. `[자동][출결벌점]`, 시험 자동 점수 등의 출처를 구별한다.
- 일반 결석 -2, 아침 미응시 -1 등의 수치는 경찰 운영 설정 사례다. 다른 학원 코드에 상수로 강제하지 않는다. 종일 결석과 교시 결석의 중복 금지 등 해당 규정도 유지한다.

### 상태별 의도

| 상태/행위 | 의도와 보존 기준 |
|---|---|
| 수업 | 출석 인정. 현재 저장 표현은 `EXCUSED`와 수업 사유를 결합하며 화면에서 CLASS로 구분한다. 일반 사유결석과 집계·벌점을 혼동하지 않는다 |
| 일반 사유결석 | 출석도 무단결석도 아니며 결석 벌점 면제. 출석률 분모·분자는 기존 집계 함수와 학원 규정의 계약을 유지 |
| 휴무·반휴 | 외출/휴가 승인 및 사용 한도·적용 교시와 연결. 드롭다운만으로 휴무권 승인·차감을 우회하지 않는다 |
| 휴무 취소 | 승인 전 기록 복구와 승인 이후 별도 정정을 구별한다. 나중에 정정한 기록을 과거 스냅샷으로 덮지 않는다 |
| 반복 수업·출석 | 학생별 기간·요일·교시를 선택한다. 미래 예약 기록을 현재 벌점으로 계산하지 않는다 |
| 수업 일괄 해제 | 관리자만 학생·기간·요일·교시를 선택하고 미리보기 후 수업만 미처리로 되돌린다. 다른 상태·시험 자동 출처는 보존하고, 확인 후 기록이 바뀌면 재확인한다. 과거·오늘 파생 계산 실패는 저장 여부와 구분하며 미래 점수는 계산하지 않는다 |
| 출석 정정 | 관리자·조교가 허용된 범위에서 저장하면 해당 자동 계산도 갱신. 설정 변경을 이유로 조교 수정 권한 자체를 확대하지 않는다 |

주요 코드: `attendance-meta.ts`, `management-policy.ts`, `services/leave.service.ts`, `services/policy-attendance.service.ts`, `services/point.service.ts`.

### 아침모의고사

- 관리자가 지정한 시작일·선택 요일·휴강일·연결 교시를 기준으로 계산한다. 시작일 미지정·비활성·제외 날짜는 임의 자동 부과하지 않는다.
- 유효한 응시·성적 근거가 있으면 설정에 따라 아침 교시를 출석으로 동기화한다. 0점과 미응시(null/기록 없음)는 구분한다.
- 승인된 사유·휴무·반휴에 해당하는 미응시에는 벌점을 부과하지 않는다. 다른 교시의 수업만으로 아침시험 면제라고 추정하지 않는다.
- 무단 미응시는 연결된 **시험 미응시 규칙**으로 계산한다. 아침 교시에 일반 결석 벌점을 이중 부과하지 않는다.
- 성적 정정·학생 연결 정정 시 변경 전후·사유를 남기고 출석 및 자동 점수의 관련 재동기화 경로를 유지한다.
- 성적 순위 상점은 아침·정기를 구분해 **월 종료 후 월별** 계산한다. 매 시험이나 설정 재저장 때 지급하지 않는다.

주요 코드: `services/exam-attendance.service.ts`, `exam-point.service.ts`, `exam-point-close.service.ts`, `exam-correction.service.ts`, `exam-point-settings.service.ts`.

### 누적시험 응시 여부 가져오기

2026-10-01 사용자 재확정: **누적시험은 성적 반영 없이 출석만 반영한다.** 누적 성적 0건을 기능 누락으로 판단하거나 성적 저장 기능을 추가하지 않는다. 오류 대응의 목표는 올바른 시험일·교시의 응시 출석 반영이다.

누적파일의 명시적 출석 가져오기는 관리규정의 아침 교시 관리 요일을 사용한다. 일반 아침 성적 자동화의 시험 요일을 임의로 확대하지 않는다. 학원별 시작일·휴강일·적용일·연동 사용 여부·교시 소유권 검사는 유지한다. 수험번호가 비어 있는 정상 답안은 제외 건수를 표시하고 다른 학생에게 추정 연결하지 않는다. 식별자 오류·중복·답안 블록 손상은 계속 거부한다. 파일에 없는 학생은 자동 결석으로 선택하지 않는다.

`services/cumulative-attendance.service.ts`는 성적 임포트와 목적이 다르다. 수험번호·실제 답안 유무로 **응시 여부만** 미리보기하고 관리자가 선택해 아침 교시 출결에 반영한다. 점수·석차·문항 통계를 만들지 않는다. 파일 누락 학생을 자동 무단 미응시로 확정하지 않고, 기존 승인 기록을 보호한다. 저장 후 실제 시험일·교시로 이동한다. 근거: [9월 18일 QA](docs/qa/2026-09-18-cumulative-attendance-import.md).

### 개근·마감

- 주간·월간 개근은 설정된 대상 교시, 기간 종료, 출결 정정, 휴무 예외를 같은 계산기로 판단한다. 진행 중인 기간에 선지급하지 않는다.
- `services/perfect-attendance.service.ts`는 날짜별 설정을 **호출 내에서** 재사용한다. 이 캐시를 학원·날짜 구분 없는 전역 캐시로 바꾸지 않는다. DB 잠금·트랜잭션·재시도 중복 방지를 유지한다.
- `services/attendance-close.service.ts`와 `/api/cron/attendance-close`를 함께 본다. 소스의 Vercel 예약은 UTC `10 15 * * *`(KST 다음 날 00:10)이다. 실제 Cron 성공 여부는 운영 실행 로그로 별도 확인한다.
- 관리자·학생의 점수 합계, 순위, 휴무 사용, 경고는 같은 원장과 조회 기간을 사용해야 한다. UI 정렬 개선을 이유로 집계 범위를 바꾸지 않는다.

## 5. 서로 혼동하면 안 되는 화면

| 화면 | 목적 |
|---|---|
| 좌석 현황·좌석 배치 설정 | 누가 어느 좌석을 쓰는지, 배치·배정 관리. 현재 교시 출결 화면이 아님 |
| 출석 관리의 좌석 보기 | 선택 날짜·교시의 학생 출결을 좌석으로 표시하고 체크. 표 보기와 동일 원장 사용 |
| 등원 현황·공용 체크인 | 실제 도착 시각 기록. 교시 출석·시험 응시·상벌점과 동일 기록이라고 간주하지 않음 |
| 휴대폰 체크 | 교시별 제출·미제출·대여·반납 및 출결 대상 연동. 출석 변경 후 대상 판정도 확인 |
| 학습 랭킹 | 학습 집계 기준의 순위. 상벌점 순위나 성적 석차를 대신하지 않음 |
| 경고 대상자 | 설정된 기간·임계값·상벌점 집계로 판단. UI 표의 최근 50건 제한으로 전체 합계를 계산하지 않음 |

등원 체크 `/[division]/check-in`은 **2026-09-17 사용자 변경 요구 이후 웹 숫자 버튼을 제거**했다. 입력칸 터치 → 기기의 숫자 키패드 → 학원 설정 자릿수 충족 시 자동 제출 → 완료 후 초기화. `type=text`, `inputMode=numeric`으로 앞자리 0을 보존한다. 과거 “키패드를 막는다”는 채팅을 근거로 readOnly/inputMode=none을 복원하지 않는다. 기기 승인 관리 경로는 `/[division]/admin/settings/rules/arrivals`.

## 6. 성적·학습 분석의 데이터 계약

- 성적 원장은 기존 가져오기 자료와 직접 입력 성적이다. 비활성 시험의 과거 성적, 날짜 미등록 직접 성적, 당시 석차·메모를 누락시키지 않는다.
- 파일 전체 응시자가 등록 학생인 것은 아니다. 해당 학원 학생 연결과 전체 응시 통계 모집단을 구분한다. 번호 오마킹·연결·채점 정정은 전용 정정 기능을 사용한다.
- 운영 API `/api/[division]/exam-analysis/{regular,morning,learning}`가 `lib/exam-preview/*`를 재사용한다. **폴더명 preview만 보고 운영에서 안 쓰는 코드라고 삭제하지 않는다.** 미리보기 전용 진입의 gate와 운영 진입을 구별한다.
- 학생 분석 `/[division]/student/exams`, 관리자 학생 분석 `/[division]/admin/exams/students/[studentId]`, 전체 분석 `/[division]/admin/exams/analysis`, 진도 설정 `/[division]/admin/exams/learning`의 연결을 함께 확인한다.
- `exam_learning_documents`는 성적 원장과 별도의 학원별 진도·문항 연결·정책·복습·시간·정정 이력 저장소다. 소유 학원, revision, 동일 요청 재시도, 행 잠금을 유지한다.
- 복수 정답 문자열의 의미가 불명확하면 재풀이 자동 채점을 보류한다. 임의 채점 규칙을 추가하지 않는다.
- 정책 적용일의 이전 값, 시험 당시 제한 시간, 비교 가능한 회차 수를 사용한다. 화면상 필터만 맞추고 계산은 현재 설정으로 돌리지 않는다.
- **학습 면담(운영자 결정 2026-10-07)**: 외부 AI 없이 규칙 기반 진단(`lib/study-diagnosis.ts`)을 쓴다. 숫자는 개인 성적표와 같은 함수(`morningStudyRows`·`morningPersonalSummary`·`reviewGroups`)에서 나오고, 기준값은 학원 설정 `examAnalysis`다. 진단은 선생님이 고치는 초안이며, 학습 면담 저장 때 서버가 다시 계산해 `interviews.diagnosis_snapshot`에 남긴다(브라우저가 보낸 진단·기준 점수는 받지 않는다). 할 일은 `interview_tasks`에 할 일마다 한 행이며 같은 학원·같은 학생의 과목·시험·지난 할 일만 연결한다.
- **학생은 할 일만 본다.** 학생 화면(`listStudentVisibleTasks`)은 공개로 표시한 확인 전 할 일의 제목·과목·시험·범위·문항·방법·기한만 받는다. 면담 내용·사유·원인·진단·질문은 학생 응답에 넣지 않는다.

## 7. 성능 개선 시 바꾸면 안 되는 결과

전체 이력을 매번 읽는 비용과 JSONB 문서 성장 위험은 실제 개선 대상이다. 그러나 단순 take/기간 제한으로 응시 모집단, 당시 석차, 전체 추이, 복습 연계, 개근 판단 자료를 잘라서는 안 된다.

권장 작업 순서:
1. 현재 라우트·SQL 호출 수·행 수·응답 크기·DB/조립/브라우저 시간을 분리 측정한다. 냉간/반복 실행을 모두 기록한다.
2. 선택 회차 상세, 기간 추이, 전체 요약을 분리하고 필요한 DB 조건·select부터 축소한다.
3. 캐시는 학원·시험·학생 권한·기간·데이터/정책 revision 경계를 정의한다. 성적 가져오기·정정·삭제·정책 변경·학습 저장 후 무효화를 검증한다. 민감한 완성 응답을 공용 캐시에 넣지 않는다.
4. JSONB를 분리할 경우 기존 문서 이관·검증·롤백, 동시 저장, revision 및 요청 중복 방지 계약을 먼저 설계한다. 이력 배열을 임의 절단하는 해결책은 금지한다.
5. 최적화 전후 동일 입력의 분석 결과·권한 차단·원장 보존을 비교한다. 수치 결과가 바뀌면 성능 작업 완료로 보고하지 않는다.

현재 확정 범위와 미확인 운영 성능은 [CURRENT_STATE.md](CURRENT_STATE.md)에 기록한다.

## 8. 변경·검증·배포 체크리스트

- 작업 시작: 현재 HEAD, `git status`, 실제 요청 경로, 관련 테스트 확인. 타 세션 미커밋 파일은 담당 확인 없이 덮거나 커밋하지 않는다. `git add -A` 금지.
- 기능 수정: 재현 → 좁은 수정 → 같은 조건 재검증. 기존 기능 중복 구현 금지.
- 업무 검증: 저장→재조회, 재시도, 정정→자동 회수, 관리자·조교·학생, 서로 다른 두 학원, 과거·오늘·미래·월경계, 사유·휴무·반휴, 수동 원장 보존을 관련 범위에서 검사.
- 결과 구분: 단위/목업 테스트, 로컬 PostgreSQL, 실제 브라우저, 운영 DB/운영 배포를 별도로 기록. 테스트 전체 통과는 운영 무결함 보증이 아니다.
- DB: 변경 전 테이블·마이그레이션 적용 기록을 읽기 전용 확인. 오래된 문서만 보고 migrate deploy/resolve/reset을 실행하지 않는다. 적용한 migration 파일의 체크섬을 바꾸지 않는다.
- 커밋·푸시·운영 배포·운영 DB 쓰기는 **이번 작업에 대한 사용자 승인 후** 수행. 과거 승인 재사용 금지. `[deploy study-hall]`은 배포 트리거이지 승인 자체가 아니다.
- 완료 기록: 변경 목적, 파일, 동작, 검증 명령·결과·범위, 미확인점, 커밋·배포 ID, 다음 작업을 CURRENT_STATE/HANDOFF에 갱신. 자격증명·개인정보·운영 원장 덤프는 문서/Git에 넣지 않는다.

## 9. 개발 후 문서 갱신 의무 (2026-09-25 사용자 확정)

모든 AI는 기능 개발·버그 수정·리팩터링·설정 변경·배포 후, 완료 보고 전에 실제 결과를 문서에 반영한다. 문서 갱신까지 작업 범위에 포함하며 별도 요청을 기다리지 않는다. 중단 또는 미완료 작업도 인계 가능한 상태로 기록한다.

- **CURRENT_STATE.md**: 확인일, 기준 커밋과 미커밋 범위, 변경 목적과 실제 동작, 관련 파일/진입점, 실행한 검증 명령·환경·결과, 미확인 사항, 남은 작업과 다음 행동을 갱신한다.
- **DEVELOPMENT_CONTRACT.md**: 사용자가 확정한 목적·운영 방식·보존 계약이 바뀔 때 갱신한다. 구현 편의로 계약을 임의 변경하지 않는다.
- **관련 전문 문서**: 설정 원칙은 ACADEMY_TEMPLATES, UI 규격은 DESIGN, 구체적인 검증 증거는 docs/qa 또는 docs/releases에 기록하고 CURRENT_STATE에서 연결한다.
- **HANDOFF.md**: 시작 경로·우선순위가 달라지면 갱신한다. 상세 상태를 복제하지 않고 현재 문서로 안내한다.
- 로컬 구현, 테스트 통과, 커밋, 푸시, 운영 배포, DB 적용을 각각 구분한다. 실행하지 않은 항목은 명시하고, 이전 테스트 결과를 이번 결과처럼 재사용하지 않는다.
- 기존 설명과 달라진 사항은 현재 안내를 고치고 필요한 과거 근거는 날짜가 있는 기록으로 보존한다. 오래된 문서의 지시가 현재 지시처럼 남지 않게 한다.
- 타 AI의 미완료 변경을 완료로 기록하거나 삭제하지 않는다. 인계 시 담당 범위·의존 작업·실패 재현 조건을 남긴다.
- 문서의 코드 경로·링크·한글 인코딩과 실제 diff를 확인한다. 문서 갱신은 커밋·푸시·배포 또는 운영 데이터 변경 승인을 대신하지 않는다.
