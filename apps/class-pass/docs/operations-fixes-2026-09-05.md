# 클래스패스 운영 안전성 수정

정책: 사용자가 선택한 **전액 수납 유지**. 카드+현금 등을 합쳐 전액을 받는 복합결제는 유지하고 예약금·잔금 기능은 추가하지 않습니다.

## 반영 범위

| 항목 | 변경 |
|---|---|
| 권한 회수 | 최신 운영자 세션 검증에 실패한 토큰이 구형 인증으로 우회하지 못하도록 차단. 정상 구형 토큰 호환은 유지 |
| 환불 | 요청 UUID를 DB에서 유일하게 처리. 같은 요청 재시도는 최초 결과 반환. 환불·변경 이력·선택적 수강 종료를 한 트랜잭션으로 저장 |
| 결제 수정 | 항목 검증을 쓰기 전에 수행하고 결제·항목·청구·이력을 원자적으로 저장. 이전 버전으로 수정 시 충돌 안내 |
| 전액 수납 | 금액·분류·무료 여부 변경으로 부분 수납이나 면제 정책 우회가 생기지 않도록 DB 검증 |
| 수강 종료 | `cancelled`와 청구 `closed` 분리. 부분환불 후 남은 금액과 원래 청구액을 보존하며 종료 가능. 종료 후 신규수납·자동 재활성화 차단 |
| 등록 | 종료된 등록을 사전 확인하여 일반적인 거절 요청이 학생 프로필·인증부터 변경하지 않도록 처리 |
| 가져오기 | 학생별 행 묶음, 거래별 중복 검사. 신규 등록·청구·복합결제를 하나의 DB 트랜잭션으로 저장. 기존 학생 프로필·인증은 유지 |
| 환불 화면 | 클릭한 거래 한 건만 기본 선택. 동일 결제 모두 선택을 별도 제공. 수강 유지/종료를 명시적으로 선택 |
| 조회 실패·학생 전환 | 저장 완료 응답은 표시용으로 보존하되 재조회 실패 시 새 쓰기를 차단. 학생 전환 시 이전 결제를 지우고 늦게 도착한 이전 응답은 무시 |
| 정산 | 미확인 거래가 있거나 화면 조회 후 거래 내역이 달라지면 일일 확인 차단. 재확정 전후 기록을 변경 불가 이력으로 보존 |
| 대량 조회 | 무결성 검사와 정산 청구·확인 조회의 페이지 누락 방지. 과거 정산에서 보관 강좌 선택 지원 |
| 명단 | `상세` 버튼을 `수납·환불`로 변경. 수강종료 필터·집계·학생 이력 표시 추가 |

## 실제 로컬 검증

- PostgreSQL 통합: 잘못된 수정의 무변경, 정상 수정의 이력 일치, 요청 재시도·변경 충돌, 타 학원 접근 차단, 전액/부분환불, 종료 상태 보존을 검증했습니다.
- 실패 주입: 실제 감사 INSERT 실패 메시지를 확인하고 결제·환불·등록·청구·항목·요청번호가 함께 롤백되는지 확인했습니다.
- 동시 DB 연결: 종료가 먼저일 때 결제 거절, 결제가 먼저일 때 종료 대기, 정정의 수강등록→결제 잠금 순서를 확인했습니다.
- 정산 SQL: 미확인·오래된 화면·잘못된 합계 거절, 같은 합계의 항목 변경 감지, 재확정 이력 및 이력 쓰기 실패 시 롤백을 검증했습니다.
- 실제 브라우저: 로컬 전용 강좌 30 / 수강등록 128에서 카드 60,000원+현금 40,000원 중 현금 10,000원 환불 → 수강 유지 → 별도 사유로 종료를 실행했습니다. DB 결과는 `cancelled / closed`, 원래 청구액 100,000원, 환불 10,000원, 환불 이력 1건·종료 이력 1건입니다.
- 실제 일일 정산: 위 수납 2건·환불 1건이 미확인일 때 버튼이 차단됨을 확인한 뒤, 거래별 확인 → 일일 확인 저장을 실행했습니다. DB의 순액 90,000원·결제자 1명과 화면이 일치하고 확인 이력 1건, manifest 버전 1이 저장됐습니다. 복합결제 행 수를 강좌 수로 잘못 표시하던 문구도 `2건`으로 수정했습니다.
- 환불창 390/768/1280px: 실제 스크린샷과 DOM 폭 측정에서 가로 잘림 없음. 모바일 종료 확인창의 필수 사유·보유액 안내와 종료 후 수납 차단을 확인했습니다.

테스트 전용 강좌·학생은 위 이름과 ID로 로컬 DB에 남겨 두었습니다. 실제 은행 송금이나 카드 단말기 취소는 실행하지 않았습니다.

## DB 반영 및 배포 경계

아래 3개 마이그레이션은 **로컬 Supabase에만 적용**했고 로컬 이력도 등록했습니다. 운영 DB, Vercel, Git push는 변경하지 않았습니다.

1. `20260905074256_payment_operations_safety.sql`
2. `20260905075836_settlement_confirmation_safety.sql`
3. `20260905081334_payment_correction_enrollment_lock_order.sql`

운영 적용은 별도 승인 후 기존 동시 작업과 파일을 구분하고 DB 백업·선택 배포 계획을 잡아야 합니다. 신규 `cancelled` 상태가 저장된 뒤에는 구버전 앱만 되돌리는 단순 롤백이 안전하지 않습니다. 기존 수강·수납 기록을 임의로 변경하거나 테이블을 삭제하지 말고 호환 가능한 복구/전진 수정 계획을 세워야 합니다.

환불 POST는 이제 `requestId` UUID가 필수입니다. 같은 업무 요청의 재시도에는 같은 UUID와 내용을 보내야 합니다. 일일 정산 확인 POST도 화면에서 조회한 `expectedManifest`가 필수입니다. 별도 연동·구형 수동 검증 스크립트는 이 계약에 맞춰 사용해야 합니다.

## 이번에 추가하지 않은 항목과 한계

- 예약금·잔금·연체 알림: 사용자 선택에 따라 제외.
- 명단의 정확한 미수금 열·통합 학생 검색·전체 업무 대시보드: 별도 조회 모델 확장이 필요하여 후속 개선으로 남겼습니다.
- 책임자 예외 승인, 수납자/마감자 분리, 세무상 매출 인식 정책: 새 운영 정책을 임의 도입하지 않았습니다.
- 정산 확정은 짧은 테이블 쓰기 잠금을 사용합니다. 실제 운영 부하에서 잠금 대기와 응답 시간을 배포 전 확인해야 합니다. 확정 후 거래 수정을 전면 금지하는 하드 마감은 아닙니다.
- 엑셀에 원본 거래번호가 없는 경우 동일 서명 거래는 검토 대상으로 표시합니다. 임의로 다른 새 요청을 만든 경우까지 같은 거래라고 단정하지 않습니다. 환불창을 닫거나 새로고침한 뒤에는 원장·실제 환불 여부부터 확인해야 합니다.
- 일반 등록 사전조회 직후 다른 작업이 종료 처리하는 경우, 등록·금융 저장은 DB가 막지만 별도 트랜잭션의 학생 프로필 준비까지 원자적으로 롤백되는 구조는 아닙니다.
- 강좌 목록 API 자체의 1,000개 초과 강좌 페이징, 실기기 QR/카메라 전체 흐름, 운영 단말기·PG·은행 대사, 운영 백업 복구와 부하 검증은 미실시입니다.
- 일반 결제 취소·환불 취소 등 기존의 다른 쓰기 경로 전체를 이번 원자적 저장 RPC로 전환한 것은 아닙니다. 이번 검증은 위에 명시한 수정 범위의 증거이며 운영 전체의 무결성을 보증하지 않습니다.
