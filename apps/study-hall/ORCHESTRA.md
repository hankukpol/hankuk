# 오케스트라 운영 규칙

여러 Claude 세션이 이 앱을 나눠 작업할 때의 통신 규약이다.
**목적은 하나 — 토큰 소비를 줄이는 것.** 품질 규칙은 `CLAUDE.md`·`DESIGN.md`·`MOBILE_DESIGN.md`에 있고 이 문서는 다루지 않는다.

세션을 열 때, 그리고 다른 세션에 메시지를 보내기 전에 이 문서를 읽는다.

---

## 왜 이게 필요한가

세션 간 메시지는 **양쪽 모두에 과금된다.** 보내는 쪽에는 출력, 받는 쪽에는 입력으로.
그리고 받은 메시지는 그 세션의 컨텍스트에 **세션이 끝날 때까지 남는다.** 800단어 보고 하나는 한 번이 아니라 그 세션의 남은 모든 요청에 실린다.

실측: 오케스트라 방식으로 하루를 돌린 결과, 같은 작업량을 단일 세션으로 할 때보다 토큰 소비가 크게 늘었다. 원인의 대부분은 메시지 길이였지 작업량이 아니었다.

---

## 1. 몇 명을 부를 것인가 — 가장 큰 절감은 여기서 나온다

메시지를 줄이는 것보다 **애초에 부르지 않는 것**이 훨씬 싸다.
레인 하나를 호출하면 그 세션이 프로젝트 문서와 관련 코드를 처음부터 다시 읽는다. 그 비용이 작업 자체보다 큰 경우가 흔하다.

**기본은 오케스트라가 직접 처리한다.** 나눠야 하는 작업만 나눈다.

| 작업 | 누가 |
|---|---|
| 한 화면·한 파일 안에서 끝나는 수정 | **담당 한 명이 구현·검증까지** |
| 문구·색·간격 변경 | **담당 한 명.** QA 호출은 화면이 실제로 바뀐 뒤 한 번만 |
| 서로 독립적인 작업 | **최대 두 담당 병렬** |
| 스키마 → 서비스 → 화면으로 이어지는 변경 | 순차로 부른다 (§7) |
| 원인을 모르는 버그 | **한 명이 먼저 좁힌다.** 못 좁히면 그때 확대 |

전 레인 동시 호출은 **오픈 전 최종 점검처럼 정말로 전 영역이 필요한 때만** 한다.

**별도 리뷰를 붙이는 경우는 셋뿐이다** — 권한, 성적 계산, DB 변경. 이 셋은 틀렸을 때 조용히 틀리고 되돌리기 비싸다. 나머지는 담당의 자체 검증으로 끝낸다.

세부 규칙:

- **같은 문서를 여러 레인이 반복해 읽게 하지 않는다.** 작은 수정에 "DESIGN.md 읽고 시작하세요"를 붙이지 않는다. 이미 그 규격 안에서 일하던 레인은 다시 읽을 필요가 없다.
- **Claude와 Codex에 같은 문제를 주지 않는다.** 한쪽이 구현하고 다른 쪽이 검증하는 구성은 문제가 정말 어려울 때만 쓴다. 보통은 한쪽이 끝까지 간다.
- **상태를 자주 조회하지 않는다.** 레인이 끝나면 보고한다. 오케스트라가 중간에 물어보면 그 레인은 하던 일을 멈추고 상태를 서술하는 데 토큰을 쓴다.
- **끝난 담당을 다시 부르지 않는다.** 공지·진행 상황 공유·"접수했습니다" 확인 같은 이유로 유휴 레인에 메시지를 보내지 않는다. 그 레인에 **줄 일이 생겼을 때만** 부른다. 커밋 완료나 다른 레인 소식은 알릴 필요가 없다.
- 초기 담당 정리 같은 **일회성 비용은 감수한다.** 그건 이후 매 요청의 중복을 없앤다.

## 2. 메시지 길이 상한

| 방향 | 상한 | 형식 |
|---|---|---|
| 레인 → 오케스트라 (보고) | **10줄** | 아래 정형 |
| 오케스트라 → 레인 (지시) | **10줄** | 아래 정형 |
| 오케스트라 → 사용자 | **필요한 만큼** | 사용자는 맥락이 없다. 여기는 줄이지 않는다 |

상한을 넘길 것 같으면 **메시지가 아니라 파일에 쓴다** (§3).

### 보고 정형

```
[레인명] 한 줄 결론
상태: 완료 | 막힘 | 진행중(N%)
파일: 건드린 파일 경로만 (내용 없이)
검증: typecheck N / lint N / test N-M
막힌 것: 있으면 한 줄. 없으면 이 줄 생략
판단 필요: 있으면 질문 한 줄. 없으면 이 줄 생략
```

### 지시 정형

```
[오케스트라] 무엇을
왜: 한 줄 (생략 가능하면 생략)
범위: 파일 또는 화면
하지 말 것: 경계가 모호할 때만
게이트: 커밋 조건
```

## 2. 쓰지 말아야 할 것

이것들이 실제로 토큰을 태운 패턴이다.

- **상대가 이미 아는 맥락 재진술.** "오픈이 이틀 남았으므로…"를 매번 쓰지 않는다. 한 번 말했으면 안다.
- **코드 블록으로 진단 결과 붙여넣기.** 파일:줄 번호만 준다. 상대가 읽을 수 있다.
- **표.** 3행 이하가 아니면 파일에 쓴다.
- **칭찬·사과·인사.** "잘 잡으셨습니다", "죄송합니다"는 토큰이다. 판단이 맞았으면 그냥 채택하고, 틀렸으면 정정만 쓴다.
- **같은 사실을 두 레인에 각각 길게 설명.** 파일에 한 번 쓰고 경로를 준다.
- **지시 번복.** 아래 §5.

## 3. 긴 것은 파일로 오간다

메시지가 10줄을 넘으면 `.orchestra/` 아래에 쓰고 **경로 한 줄만** 보낸다.

```
.orchestra/STATUS.md        각 레인이 자기 구역만 갱신. 오케스트라는 이것만 읽는다
.orchestra/<주제>.md         진단·측정·설계 문서. 예: exam-import-findings.md
```

`.orchestra/`는 gitignore 대상이다 — 작업 중 소통이지 저장소 이력이 아니다.
결론이 코드나 문서로 남을 가치가 있으면 그때 정식 파일로 옮긴다.

### STATUS.md 형식

레인마다 **정확히 4줄**. 다른 레인 구역을 건드리지 않는다.

```
## 조교
상태: 진행중 — exam_scores.updated_at 마이그레이션
검증: test 610/619 (9건 실패, 수정 중)
막힌 것: 없음
```

오케스트라는 보고를 기다리는 대신 이 파일을 읽는다.

---

## 4. 검증은 한 번만 한다

- **레인이 돌린 검증을 오케스트라가 다시 돌리지 않는다.** 레인이 "test 619/619"라고 하면 그대로 믿는다.
- 오케스트라는 **커밋 직전에 한 번만** 통합 트리에서 돌린다. 그게 여러 레인의 변경이 합쳐진 상태를 보는 유일한 시점이다.
- 레인은 자기 변경만 검증한다. 다른 레인 때문에 깨진 것은 **고치지 말고 보고**한다 (§6).

---

## 5. 지시를 바꾸기 전에

지시 번복은 가장 비싼 실수다. 원래 지시 + 정정 + 레인의 되돌리기까지 세 번 과금된다.

**규칙: 사실을 다 모으기 전에 지시하지 않는다.**

특히 오케스트라는 다음을 착각하기 쉽다.

- **운영 DB 데이터로 업무 규칙을 유추하기.** 지점마다 관례가 다르다. 한 지점 데이터로 다른 지점 규칙을 결론내지 않는다.
- **레인이 사용자와 직접 나눈 대화를 모르기.** 레인이 사용자에게 직접 들은 사실이 있으면 오케스트라의 추론보다 우선한다. 레인은 그런 사실을 들으면 **즉시 한 줄로** 오케스트라에 알린다.
- **코드를 덜 읽고 설계 판단하기.** "이 기능이 없다"고 결론내기 전에 `grep` 한 번 더 한다. 이미 있는 경우가 많다.

업무 사실(학원의 운영 방식, 명칭, 규칙)이 갈리면 **추론하지 말고 사용자에게 묻는다.** 그게 가장 싸다.

---

## 6. 파일 소유권

한 파일은 한 레인만 고친다. 겹치면 오케스트라가 순서를 정한다.

- `prisma/schema.prisma`는 **모델 단위로** 나눈다. 파일 단위로 잠그면 아무도 못 움직인다.
- 새 마이그레이션 디렉터리는 오케스트라가 타임스탬프를 배정한다. 두 레인이 같은 날짜를 쓰면 순서가 무너진다.
- **커밋은 오케스트라만 한다.** 저장소 git 인덱스가 하나라 동시 커밋은 서로를 밟는다. 레인은 "커밋 가능"만 보고한다.

---

## 7. 사용자에게 가는 말

레인은 사용자에게 직접 보고하지 않는다. 오케스트라가 취합한다.
단, **레인이 사용자에게 직접 질문을 받거나 답을 들은 경우**는 예외이며, 그 사실을 즉시 오케스트라에 한 줄로 전달한다.

오케스트라의 사용자 보고는 짧게 줄이지 않는다. 사용자는 코드도 다른 세션도 보지 않으므로, 여기서 아낀 토큰은 오해로 되돌아온다.

---

## 8. Claude와 Codex의 경계

| | 범위 |
|---|---|
| Claude | `main` 브랜치, 공용 개발 서버(3000), 최종 통합, 커밋·배포 |
| Codex | 별도 워크트리 (`D:/Codex/worktrees/*`) |

**같은 문제를 양쪽에 주지 않는다.** 한쪽이 구현하고 다른 쪽이 검증하는 구성은 §1의 리뷰 대상 셋(권한·성적 계산·DB 변경)에서, 정말 필요할 때만 쓴다.

품질 기준은 이 문서가 아니라 각 규격 문서를 따르며, 다음은 어떤 절감 규칙보다 우선한다.

- 필수 테스트 통과
- `MOBILE_DESIGN.md` 모바일 기준
- A4 인쇄 출력 기준

## 9. 세션을 새로 열 때

새 레인 세션의 첫 지시에 이것만 준다.

```
apps/study-hall/ORCHESTRA.md 를 읽고 그 규약대로 보고해 주세요.
담당: <화면 또는 파일 범위>
지금 할 것: <한 줄>
```

프로젝트 배경을 다시 설명하지 않는다. `CLAUDE.md`와 `DESIGN.md`가 이미 그 일을 한다.
