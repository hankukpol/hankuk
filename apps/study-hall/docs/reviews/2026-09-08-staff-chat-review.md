# 직원 채팅 리뷰와 포털 실시간 전환 검토

기준: 2026-09-08, `ad46b67`까지 배포된 코드 및 현재 작업 사본. 다른 세션의 출결·수납·학생 작업은 수정하지 않았다. 이번 변경은 로컬에만 있으며 커밋·운영 배포·운영 DB 변경은 하지 않았다.

## 판단

채팅의 확인된 결함은 로컬에서 수정한다. **포털 브리지에 Supabase 세션을 추가하는 변경은 이번에 적용하지 않는다.** 기술적으로 구현 가능하지만, 삭제 본문 노출과 공용 Auth 세션의 부수 효과를 먼저 정리해야 한다. 기존 폴링과 로그인 경로는 유지한다.

시간만 있는 기존 커서의 동률을 자르지 않기 때문에 200건은 목표 크기이며 같은 시각의 변경 묶음은 이를 넘을 수 있다. 무제한 일반 조회로 바꾸지는 않았다. DB 트랜잭션의 커밋 순서까지 보장하는 변경 로그 커서는 아니므로 장시간 지연 커밋까지 완전 보장한다고 주장하지 않는다.

## 포털 인증 경계

- 브리지는 `consume_portal_launch_token`에 `STUDY_HALL` 앱 키와 입력 토큰을 전달한다. 저장소 SQL은 해시·앱 키·만료·미사용 조건, 행 잠금과 소비 UPDATE를 사용한다. 이번에 운영 함수가 이 SQL과 동일한지 재조회하지 않았다.
- 소비 후 활성 admin을 `consumed.user_id`로 조회하고 역할과 지점을 검사한다. 실패하면 앱 쿠키를 발급하지 않는다. 성공 시 303으로 POST를 GET으로 전환한다.
- 세션 발급을 추가한다면 이 검증이 **모두 끝난 뒤에만** 수행해야 한다. `getUserById` → `generateLink` → `verifyOtp` 각각의 반환 사용자 ID가 검증된 `admin.userId`와 일치해야 한다. 링크·해시·액세스 토큰·쿠키·service role 키를 응답이나 로그에 노출해서는 안 된다.
- 메일 주소만 신뢰하여 세션을 발급하면 조회 사이 이메일 변경 등에서 사용자 혼동 가능성이 생긴다. 검증 중 실패한 쿠키를 본 응답에 미리 적용해서도 안 된다.
- 실패는 앱 로그인을 실패시키지 않아야 한다. 앱 세션 응답을 먼저 구성하고, 제한 시간·취소 가능한 별도 Auth 호출과 임시 쿠키 버퍼를 사용해야 한다. 단순 `try/catch`만으로는 호출 지연이나 이미 기록된 부분 쿠키를 막을 수 없다. 실패 로그는 원문 비밀값 없이 단계·오류 분류만 남긴다.
- 이번에는 발급 코드를 추가하지 않았으므로 새 Auth 장애가 기존 포털 로그인에 추가될 경로가 없다. 실패 시 폴링 전환을 새 발급 코드로 실증했다고 주장하지 않는다.

## 전환을 보류한 이유

### 1. 삭제 본문이 브라우저 읽기 권한에서 가려지지 않는다

`supabase/migrations/20260909001000_study_hall_chat_realtime.sql`(저장소 루트 기준)은 `authenticated`에 채팅 테이블 SELECT를 주고, 지점 자격만 검사한다. `deletedAt` 행을 제외하거나 `body` 열을 가리는 정책은 없다. 서비스는 삭제 시 본문을 보관하며 API 직렬화 단계에서만 빈 문자열로 바꾼다.

따라서 **동일 지점의 인증된 직원은 브라우저 클라이언트를 직접 조작해 삭제 본문을 읽을 수 있는 구조**다. UI가 Realtime 페이로드를 사용하지 않는다는 원칙은 좋은 구현 분리이지만 보안 경계는 아니다. 이 위험은 이미 직접 로그인 사용자에게도 해당할 수 있다. 실제 운영 공격이나 조회를 수행하지 않았으며, 저장소의 권한·정책·삭제 코드를 조합한 판정이다.

삭제 행을 RLS에서 단순 제외하면 삭제 신호 전달에 영향을 줄 수 있다. 삭제 본문 별도 보관, 본문 제거의 보존 정책, 본문 없는 Broadcast 신호 등 중에서 요구사항에 맞는 방식을 정한 후 검증해야 한다. 기존 본문을 임의로 영구 삭제하거나 적용 완료된 정책을 이번 작업에서 변경하지 않았다.

### 2. 공용 Auth 세션의 부수 효과

현재 `app/api/auth/logout/route.ts`는 `auth.signOut()`을 옵션 없이 호출한다. Supabase 기본값은 `scope: 'global'`이므로 같은 사용자의 다른 Supabase 세션 갱신 토큰도 폐기할 수 있다. 새 세션이 생기는 범위를 포털 사용자 전체로 넓히기 전에 로그아웃 범위를 정리해야 한다. [공식 signOut 문서](https://supabase.com/docs/reference/javascript/auth-signout)

포털·class-pass·interview-pass는 자체 앱 세션을 사용하므로, 이를 “다른 앱이 즉시 전부 로그아웃된다”라고 해석하면 안 된다. Supabase 세션 폐기와 각 앱 JWT 수명은 별개다. 다만 다른 Supabase 로그인과 공용 프로젝트의 단일 세션·비활성 시간 제한·쿠키 도메인 설정은 이번에 운영에서 확인하지 않았다.

### 3. 30일 앱 세션과 Auth 갱신

`lib/session-tokens.ts`의 관리자 앱 토큰은 30일이다. Supabase 액세스 토큰의 통상 1시간은 전체 세션의 수명이 아니다. refresh token이 유효하면 갱신할 수 있으며, 프로젝트의 세션 제한 설정에 따라 중단될 수 있다. [공식 세션 문서](https://supabase.com/docs/guides/auth/sessions)

현재 최상위 middleware는 `updateSession`을 호출하지 않는다. 설치된 `@supabase/ssr`의 브라우저 클라이언트는 `autoRefreshToken: isBrowser()`와 `persistSession: true`를 사용한다. 따라서 브라우저에서의 갱신·복귀 시 갱신·네트워크 장애·세션 폐기 상황을 확인해야 한다. 만료 시 기존 `subscribeToChatSignal`의 폴링 경로를 유지해야 하며, Auth 오류 때문에 앱의 30일 세션을 지우면 안 된다. 기존 실시간 모듈은 재작성하지 않았다.

## 검증 범위

포털 라우트는 실제 소스를 실행하되 RPC·Prisma·쿠키 발급 의존성을 격리한 11개 테스트로 성공/재사용/만료/출처/역할/지점/비활성 계정/리다이렉트 실패 경계를 검증했다. 이것은 운영 RPC의 동시 소비 테스트를 대체하지 않는다.

채팅 DB 분기는 Prisma 대역으로 실행하는 회귀 테스트를 추가했다. 운영 DB 자격 증명을 내려받거나 운영 메시지를 작성하지 않았다. 통합 검증은 별도 `.local/test-*` 사본에서 빌드하므로 실행 중인 원본 개발 서버의 `.next`를 덮어쓰지 않는다.
