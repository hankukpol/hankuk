# 클래스패스 운영·수강등록·수납·정산 점검

점검일: 2026-09-05 · 대상: 현재 로컬 작업본과 로컬 미리보기

## 1. 결론

기본 운영 기능은 갖춰져 있지만, 현재 상태를 “운영상 문제가 없다”고 판단할 수는 없습니다. 우선 손볼 부분은 **권한 회수, 환불 재시도, 결제 수정의 저장 순서, 부분 환불 후 수강 종료**입니다. 이후 미수금 관리와 정산 마감 절차를 개선하는 순서가 적절합니다.

이번 점검은 구현 요청이 아닌 확인·제안 요청에 따른 감사입니다. 애플리케이션 코드와 운영 데이터는 수정하지 않았으며, 보고서와 메모리 모의 재현 스크립트만 추가했습니다. 작업 폴더에는 기존 미커밋 변경과 동시 진행 중인 변경이 있어, 아래 결과는 배포된 운영 버전의 상태를 보증하지 않습니다.

## 3. 먼저 수정할 항목

### 3.1 권한 회수 후 기존 로그인 차단이 우회될 수 있음

현상: 최신 운영자 세션 검증이 실패해도 구형 관리자·직원 인증으로 다시 넘어갑니다. 최신 토큰에는 구형 `sessionVersion`이 없으며, 이 값이 없을 때 기본값 1을 적용합니다. 따라서 구형 세션 버전이 1인 환경에서는 회수된 최신 세션도 통과할 수 있습니다.

재현: 유효하게 서명된 토큰을 읽은 다음 단계에서, 세션 검증이 회수 상태로 실패하도록 모의 설정했습니다. 관리자와 직원 모두 `error: null`로 통과했습니다. 구형 버전을 2로 바꾼 대조 실험에서는 직원 요청이 401로 차단됐습니다.

이것은 임의의 비로그인 사용자가 접속한다는 의미가 아닙니다. **이전에 발급받은 미만료 토큰과 구형 버전 1이라는 조건**이 필요합니다. 운영 환경의 현재 버전 값이나 실제 악용 여부는 확인하지 않았습니다.

근거: [관리자 인증 분기](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/src/lib/auth/authenticate.ts:84>), [직원 인증 분기](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/src/lib/auth/authenticate.ts:152>), [기본 버전](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/src/lib/auth/session-version.ts:7>).

권고:

- 최신 식별자·세션 범위를 가진 토큰은 최신 검증에 실패하면 즉시 401을 반환합니다.
- 구형 인증은 실제 구형 토큰에만 허용하고 종료 시점을 정합니다.
- 로그아웃, 직원 비활성화, 지점 권한 삭제, PIN 변경 후 기존 토큰을 각각 검증하는 테스트를 추가합니다.

완료 기준: 위 조치 후 기존 관리자·직원 토큰으로 보호 API를 호출하면 모두 거부되며, 정상 활성 세션과 다른 지점 격리는 유지됩니다.

### 3.2 환불은 저장됐는데 실패로 표시되고 재시도하면 중복 기록됨

현상: 환불 저장 RPC가 성공한 뒤 결제 내역 재조회가 실패하면, 저장된 환불 ID를 서비스의 복구 목록에 담기 전에 예외가 발생합니다. 호출자는 실패를 받지만 환불 기록은 남습니다. 요청 고유번호가 없어 동일한 부분 환불 재시도가 별도 환불로 처리됩니다.

재현: 10만 원 결제에 1만 원 환불을 저장한 직후 조회 오류를 주입했습니다. 첫 요청은 실패했으나 원장에는 1만 원이 남았습니다. 같은 요청을 재시도하자 총 2만 원, 2건이 됐습니다. DB RPC 자체는 모의 구현이며, 저장 성공 후 실제 서비스 코드의 오류·재시도 동작을 검증한 결과입니다.

주의: **실제 은행 송금이 두 번 실행됐다는 의미는 아닙니다.** 현재 환불창은 카드 단말기 취소를 별도로 안내합니다. 확인한 문제는 장부 기록의 중복입니다.

근거: [환불 저장·재조회·복구 순서](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/src/lib/payments/service.ts:2059>), [환불 RPC](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/supabase/migrations/202605070007_atomic_refund_bundle.sql:64>).

권고:

- 사용자가 시작한 환불 1회에 고유 요청번호를 부여하고 DB에서 유일성을 보장합니다. 같은 번호의 재시도는 기존 결과를 반환해야 합니다.
- 환불 원장·항목·이력을 하나의 트랜잭션에서 확정합니다.
- 확정 후 조회·캐시 갱신 실패는 저장 실패와 구분합니다. 이미 확정한 환불을 후처리 오류 때문에 삭제하는 복구 방식도 함께 검토합니다.
- 화면에 “저장 완료, 내역 새로고침 필요” 또는 요청번호로 처리 결과를 확인하는 경로를 둡니다.

완료 기준: 응답 유실·조회 실패·연속 클릭·같은 요청 재전송에도 동일 요청번호의 환불은 정확히 1건만 남습니다.

### 3.3 결제 수정 API가 검증 전에 원장을 바꿈

현상: 결제 총액을 먼저 UPDATE하고, 이후 세부 항목 합계가 총액과 일치하는지 검사합니다. 검증 실패 시 금액 UPDATE가 되돌아가지 않습니다.

재현: 기존 결제 10만 원을 총액 20만 원, 항목 합계 10만 원으로 수정 요청했습니다. 오류가 반환됐지만 총액은 20만 원, 항목은 10만 원으로 남았고 변경 이벤트는 0건이었습니다.

확인 범위는 실제 `updatePayment` 함수와 해당 PATCH API입니다. 현재 일반 화면이 이런 잘못된 입력을 만들어 보낸다고까지 확인한 것은 아닙니다.

근거: [먼저 실행되는 UPDATE](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/src/lib/payments/service.ts:1884>), [뒤늦은 항목 검증](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/src/lib/payments/service.ts:1895>), [PATCH 진입점](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/src/app/api/payments/[id]/route.ts>).

권고: 모든 검증을 첫 쓰기 전에 끝내고 총액·항목·이력·청구 상태를 원자적으로 저장합니다. 금액·결제수단 수정은 기존 정정 처리로 통일하고 일반 수정은 메모 등 비금전 항목에 한정할지도 검토합니다.

완료 기준: 검증 실패 시 관련 테이블이 모두 원래 상태이고, 정상 수정은 원장과 항목 합계 및 변경 이력이 일치합니다.

### 3.4 부분 환불 후 수강 종료가 막힘

현상: 수강 상태를 환불로 변경하는 API는 결제액에서 환불액을 뺀 값이 0보다 크면 거부합니다. 일반 상태 수정에서도 환불 상태 변경은 전용 API로만 하도록 제한합니다. 이미 이용한 수강료를 남기고 나머지만 반환하는 중도 종료를 별도로 표현하기 어렵습니다.

재현: 10만 원 수납, 7만 원 환불, 3만 원 보유 상태에서 종료 API가 409를 반환했고 수강 상태는 `active`로 유지됐습니다. 여기서 7만 원은 동작 설명을 위한 예시이며 법정 환불액을 산정한 것이 아닙니다.

근거: [잔액이 남으면 거부](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/src/app/api/enrollments/[id]/refund/route.ts:62>), [수강 상태 자동 연동](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/supabase/migrations/202605070007_atomic_refund_bundle.sql:195>).

권고:

- 수강 상태: 수강중 / 일시정지 / 중도종료 / 수료 / 전반.
- 수납 상태: 미납 / 부분수납 / 완납 / 부분환불 / 전액환불.
- 환불 화면에서 “수강 유지”와 “수강 종료”를 금액과 별도로 선택합니다.
- 종료 시점에 QR·교재 수령 자격·좌석·출결 대상과 이후 청구를 일관되게 처리합니다.
- 교재비를 보유하는 경우도 별도 정책으로 명확히 합니다. 현재 전용 상태 API는 결제 전체 잔액을 보고, 환불 RPC의 상태 연동은 수강료 기준이어서 기준도 통일할 필요가 있습니다.

응시 정지를 중도 종료의 상시 대체 수단으로 쓰는 것은 상태 의미가 달라 권하지 않습니다.

## 4. 수납·등록 운영 개선

### 4.1 엑셀 가져오기: 복합결제 안내대로 입력해도 중복으로 탈락

복합결제는 카드·현금 등을 행으로 나누라고 안내하지만, 동일 파일 안 중복 키는 거래가 아닌 학생 학번 또는 이름·연락처·생년월일입니다. 같은 학생의 카드 6만 원 + 현금 4만 원을 두 행으로 입력하면 첫 행은 신규 생성 예정, 두 번째는 중복으로 판정됩니다. 실제 미리보기 함수에서 재현했습니다.

근거: [복합결제 분리 안내](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/src/lib/payments/bulk-import.ts:309>), [학생 단위 중복 키](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/src/lib/payments/bulk-import.ts:334>).

추가 코드 확인: 신규 학생 가져오기는 수강등록을 먼저 만든 뒤 청구정보 없이 수강료 결제를 호출합니다. 신규 등록 생성 함수에는 청구정보 생성이 없고, 결제 서비스는 청구정보 없는 양수 수강료 결제를 거부합니다. 따라서 신규 등록만 남고 결제는 실패하는 경로가 있습니다. 저장소의 마이그레이션에서 이를 자동 보완하는 등록 INSERT 트리거는 찾지 못했습니다. 이 추가 경로는 실제 DB로 재현하지 않았으므로 통합 검증이 필요합니다.

### 4.2 예약금·잔금 결제

현재 수납 합계는 남은 청구액과 정확히 같아야 합니다. 예를 들어 수강료 60만 원 중 오늘 20만 원만 받고 40만 원을 나중에 받는 방식은 허용되지 않습니다. 여러 결제수단을 합쳐 전액을 받는 혼합결제와 카드 할부는 이것과 다른 기능입니다.

근거: [서비스의 전액 일치 검증](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/src/lib/payments/service.ts:1415>), [수납 화면](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/src/components/payments/EnrollmentPaymentDrawer.tsx>).

### 4.3 환불창 기본 선택 축소

로컬 UI에서 계좌이체 3만 원 결제의 환불을 눌렀는데, 같은 수강등록·같은 분류의 카드·현금까지 3건이 선택됐고 환불 예정 합계는 10만 원이었습니다. 클릭한 한 건과 동일 결제 묶음만으로 범위를 제한하지 않으며, 후보들의 남은 금액 전체를 기본 입력합니다.

근거: [환불 후보와 기본 선택](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/src/components/payments/RefundModal.tsx:116>).

### 4.4 학생 명단을 수납 업무의 출발점으로 개선

명단에는 수강 상태가 있지만 미납액·부분 수납 여부가 바로 보이지 않습니다. 이름을 누르면 이력, 상세를 누르면 수납 서랍으로 들어가는 구조라 수납을 자주 하는 직원에게는 목적지가 모호합니다. 학생 검색 기능 자체가 없는 것은 아닙니다.

권고:

- 명단에 수납 상태와 잔액을 표시하고 미납·연체만 필터링합니다.
- `상세` 대신 또는 함께 `수납·환불` 바로가기를 제공합니다.
- 전체 강좌를 가로지르는 학생 검색에서 현재 수강·잔액·최근 수납을 함께 보여줍니다.
- 등록 완료 화면에서 결제 결과, 로그인 안내, 추가 등록할 강좌를 명확히 이어줍니다.
- 대시보드의 오늘 할 일에 미확인 입금·기한 지난 미납·처리 중 환불을 추가합니다. 학생 알림 자동 발송은 별도 운영 승인과 정책 설계 후 도입합니다.

## 5. 정산 개선

### 5.1 기존 기능과 보완할 부분

일일·월별 정산, 결제수단별 집계, 영수증 번호, 거래별 확인, 일일 정산 확인 및 확인 이후 변경 감지는 이미 있습니다. “마감 후 변경을 전혀 알 수 없다”는 상태는 아닙니다.

로컬 과거 일자 조회에서 수납 4,445,000원, 환불 820,000원, 순액 3,625,000원이 표시됐고 화면상 산술 관계는 일치했습니다. 이는 기존 테스트 데이터의 화면 확인이며 운영 매출 검증이 아닙니다.

다만 거래별 미확인 건이 있어도 일일 정산 확인 버튼이 활성화되고, 서버의 확인 함수도 미확인·불일치 건을 선행 조건으로 검사하지 않습니다. 현재 확인 함수는 날짜·지점의 스냅샷을 덮어쓰는 방식입니다.

근거: [변경 감지](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/src/lib/payments/settlement-confirmation.ts:249>), [정산 확인 저장](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/src/lib/payments/settlement-confirmation.ts:277>), [확인 버튼 제한 조건](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/src/app/(admin)/dashboard/settlements/daily/page.tsx:399>).

권고하는 절차:

1. 담당자가 카드 단말기·계좌 입금·현금 시재와 시스템 수납을 대조합니다.
2. 거래별 확인을 끝내고 차이금액과 미해결 사유를 확인합니다.
3. 일일 마감은 미확인 건이 0이거나 책임자의 예외 승인이 있을 때만 합니다.
4. 화면에서 본 데이터 버전과 서버 마감 데이터 버전이 같아야 합니다. 중간에 거래가 추가됐다면 다시 검토하도록 합니다.
5. 마감 뒤 변경은 재개방 사유·변경자·재확인자·이전 스냅샷을 보존합니다.

직원이 적다면 수납자와 승인자를 반드시 다른 사람으로 강제하기보다, 단독 처리 예외를 기록하는 식으로 운영 현실에 맞추면 됩니다.

### 5.2 현금 흐름과 매출 분류를 분명히 하기

포인트·무료·할인·홈페이지 결제를 카드·현금 입금과 같은 의미로 읽지 않도록, 운영 보고에는 다음을 구분하는 편이 좋습니다.

- 실제 받은 현금성 금액: 카드, 계좌, 현금 및 확인된 외부 결제.
- 청구·수납 실적: 수강료·교재비·할인·포인트 적용 내역.
- 환불과 정정: 실제 환불과 오입력 정정을 구분한 원인별 합계.
- 미수금: 아직 받지 않은 금액과 기한.

이는 업무 화면의 구분 제안이며 세무상 매출 인식 기준을 판정한 것이 아닙니다.

### 5.3 종료 강좌와 대량 데이터

일일 정산의 강좌 선택은 `activeOnly=1`로 목록을 불러옵니다. 과거 정산에서는 종료·보관 강좌를 직접 골라 조회할 수 있도록 “종료 강좌 포함” 옵션을 권합니다.

정산 무결성 검사에는 기본 2,000건을 대상으로 `.limit(maxEnrollments + 1)`을 요청하는 코드가 있으나, 로컬 Supabase 설정은 응답 상한 1,000건입니다. 이 상한이 적용되면 1,000건만 받고도 잘림 표시가 꺼질 수 있습니다. 운영 상한값은 확인하지 않았습니다. 청구 스냅샷 일괄 조회의 단일 `in` 요청도 큰 명단에서 점검해야 합니다. 일반 정산 결제 조회에는 이미 페이지 조회가 적용된 경로가 있으므로 전체 정산 조회가 모두 1,000건에서 잘린다고 단정하지 않습니다.

근거: [강좌 목록 조건](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/src/app/(admin)/dashboard/settlements/daily/page.tsx:235>), [검사 조회·잘림 판정](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/src/lib/payments/integrity.ts:321>), [API 응답 상한](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/supabase/config.toml:8>), [청구 스냅샷 일괄 조회](<D:/코딩/학원 포탈 프로그램/hankuk/apps/class-pass/src/lib/payments/service.ts:1672>).

## 6. 추천 실행 순서

| 단계 | 실행 범위 | 통과 기준 |
|---|---|---|
| 1. 정합성·권한 | 권한 회수, 환불 중복 방지, 결제 수정 원자성 | 실패·재시도·회수 토큰 테스트 및 실제 격리 DB 검증 |
| 2. 수강 생애주기 | 부분 환불 후 종료, 정지·수료·전반 구분 | 금액과 무관한 상태 전환 및 QR·좌석·배부 자격의 일관성 |
| 3. 수납 실무 | 엑셀 가져오기, 부분 수납 정책, 잔액 표시, 안전한 환불 기본값 | 직원이 등록→수납→잔금→환불을 우회 입력 없이 처리 |
| 4. 정산 통제 | 대사·미확인 처리·마감·재개방, 과거 강좌, 대량 조회 | 원장·화면·내보내기 합계 일치와 변경 책임 추적 |

권장 업무 흐름은 **학생 통합검색 → 수강·청구 확정 → 전액/부분/면제 수납 → 영수증·인증 안내 → 독립된 수강 상태 관리 → 일일 대사 → 마감·재개방 이력**입니다.

구현에 앞서 운영자가 정하면 좋은 항목은 예약금 허용 여부, 중도 종료 후 이용권 정책, 환불·마감 승인 권한입니다. 세 가지 정책이 정리되면 화면과 데이터 상태를 일관되게 설계할 수 있습니다.
